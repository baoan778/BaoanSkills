# Skill review rubric

Use this rubric before adding a skill to the public allowlist or making a
substantial change to an existing public skill. Structural checks are necessary
but not sufficient; review the skill as an instruction interface that an agent
will execute.

## 1. Discovery

- The description states the capability and the situations where the skill is
  the right choice.
- The description excludes a common adjacent workflow when that prevents
  misrouting.
- The display name and short description are specific. Do not ship placeholder
  text such as "Security skill" or "Ctf Web".
- The default prompt names the skill with `$skill-name` and describes a concrete
  authorized outcome.
- Routing in `docs/ROUTING.md` has been checked for overlap.

## 2. Scope and authorization

- **Authorized use only** appears near the top of the entrypoint.
- The skill defines who may use it and the environments where it applies.
- Active-testing steps require scope and written authorization.
- Non-goals and unsafe adjacent uses are explicit where ambiguity is likely.
- The skill does not imply that a public target, sample, or tool grants
  permission.

## 3. Technical quality

- Required inputs and preconditions are clear.
- The workflow distinguishes hypotheses, observations, and evidence.
- Commands or scripts are deterministic, testable, and use placeholders rather
  than live credentials or private target data.
- The output section identifies the expected deliverable and how to verify it.
- Claims that can drift, such as tool flags and version-specific behavior, have
  an appropriate verification step.
- A realistic small task can be completed from the entrypoint and linked
  references without hidden knowledge.

## 4. Progressive disclosure

- `SKILL.md` contains shared routing, constraints, workflow, and output rules.
- Mode-specific detail lives under `references/` and is directly linked from
  the entrypoint.
- Bare Markdown filenames mentioned in prose resolve from the skill root or
  the referring document.
- There are no root-level topic documents other than `SKILL.md`.
- Scripts referenced by the entrypoint exist and are named exactly.
- Content is not duplicated across several references merely to inflate the
  library.

The layout check reports advisory warnings above 500 lines. The public-skill
regression test enforces the 500-line entrypoint ceiling, while the standalone
layout check also hard-fails above 700 lines or 6,000 words.

## 5. Safety and privacy

- Examples use documentation placeholders, loopback, RFC 1918 addresses, or
  clearly synthetic targets.
- No real credentials, private keys, personal data, internal hostnames, or
  maintainer-specific absolute paths are present.
- Destructive actions have preconditions and a stop condition.
- The skill does not normalize unauthorized persistence, evasion, or data
  exfiltration.

## 6. Provenance and licensing

- `license`, `author`, and `source` are accurate.
- Third-party material has a pinned 40-character commit, exact upstream path,
  complete license evidence, and a concrete modification summary.
- CC BY-SA material remains under CC BY-SA 4.0.
- The file-level lock is regenerated after every public-skill change.

## 7. Knowledge-base imports

- The public artifact is new synthesis or path-level metadata, not a copied
  writeup, screenshot, binary, archive, or scanner plugin.
- Raw corpus bodies, challenge flags, captures, credentials, private target
  data, NASL content, and machine-specific paths are absent.
- Every published path is relative and every referenced local resource either
  exists or is explicitly documented as unavailable.
- A hash or manifest entry is not treated as a license, safety review, or
  authorship claim.
- The manifest is generated by `scripts/build_kb_manifest.py`, reviewed for
  unexpected additions, and checked after every corpus change.
- Retrieval guidance routes execution to a specialized CTF skill and tells the
  reader to verify version-specific behavior before use.

## 8. Validation and review

Run the complete development suite from the repository root:

```bash
python -m pip install -r requirements-dev.txt
python -m pytest
python scripts/build_kb_manifest.py --check
python scripts/check_resources.py
python scripts/check_skill_layout.py
python scripts/check_release_readiness.py --strict
```

A maintainer should also inspect the rendered Markdown and scan for routing
overlap that automated tests cannot detect. Reject or return a skill for changes
when its authorization boundary, provenance, or technical verification is
unclear.
